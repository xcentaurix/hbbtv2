HbbTV 2.0 for enigma2 - how it is built
=======================================

What comes out
--------------
Three packages (ipk) for a Dreambox running an OpenViX image built from the same tree (dm900 tested):

  1. WebKit   libwpewebkit-2.0-1   WPE WebKit 2.54.0 with our patches; also pulls in its own libraries (icu 78, libsoup 3,
                                   libepoxy, harfbuzz, woff2, ...) as ordinary dependencies. Provides "wpewebkit".
  2. ORB      orb                  Open Red Button HbbTV engine: libORBCore.so.1, libORBHost.so.1, the JavaScript polyfill and
                                   the two modules that are loaded by path, all under /usr/lib/orb/
  3. Plugin   enigma2-plugin-extensions-wpehbbtv
                                   /usr/bin/wpe_fb (the embedder that renders the application on the framebuffer and hosts ORB)
                                   and the enigma2 plugin (WPEHbbTV: remote control forwarding, decoder hand-over to the live TV)

The plugin depends on orb, orb and the plugin depend on WebKit (shared library dependencies are found automatically).
The layer also has a fourth recipe, wpe-shot, which only builds the bring-up tools of the early experiment; it is not needed.

The pieces of the layer (meta-hbbtv2/)
--------------------------------------
  conf/layer.conf                               the layer (depends on core, openembedded-layer, webkit)
  recipes-browser/wpewebkit/wpewebkit_%.bbappend
        appends to meta-webkit's wpewebkit_2.54.0.bb: PACKAGECONFIG (no GBM/DRM/Wayland: WPE Platform API, SHM, vendor EGL/GLES2,
        media, mediasource), and patches 0001-0013 (files/), see below
  recipes-browser/wpewebkit/files/0001..0013    WebKit patches, applied on top of the tarball and the two patches of the base recipe:
        0001-0002  build without GBM/DRM                      0007       application/vnd.hbbtv.xhtml+xml is XHTML
        0003-0006  vendor EGL (Broadcom V3D): default EGL     0008-0012  <video> on the hardware video plane (dvbvideosink hole
                   display, no GL fence, SHM read-back only              punch), decoder position/seeking, decoder hand-over
                   of the damaged regions                                with the embedder, view scale, dry run for tests
        0013       frame read-back through an ION pixmap surface (4-9x faster than glReadPixels)
  recipes-graphics/libepoxy/libepoxy_%.bbappend  libepoxy for the vendor EGL (no X11, BROADCOM_PLATFORM)
  recipes-hbbtv/orb/orb_git.bb                  ORB: fetches OpenRedButtonProject/orb at a pinned commit (SRCREV) and applies
        orb/files/0001..0004 (ORB_PLATFORM_LIB, two fixes in the JavaScript polyfill, 0004: an application can be started as a broadcast-related one of a given service without an AIT). files/CMakeLists.txt builds
        libORBCore, libORBHost, libORBPlatformImpl.so (ORB's platform mock + orb_platform_wpe.cpp) and libORBWebExt.so
        (orb_ext.c); the polyfill (hbbtv.js, iframe.js, dash.all.min.js, playerpage.html) is made by ORB's own makefile,
        which only concatenates files (no node needed).
  recipes-hbbtv/wpe-plugin/enigma2-plugin-extensions-wpehbbtv_1.0.bb
        builds wpe_fb (source: recipes-hbbtv/wpe-shot/files/wpe_fb.c) and installs it with the plugin, run_wpe.sh, fonts.conf
        and two test pages. The ipk "control" file is generated by OE from the recipe (postinst: "restart Enigma2").

1. Prerequisites
----------------
  - The OpenViX build environment (here: /home/alpha/openvix/build-enviroment, build dir builds/openvix/developer/dm900), Linux
    or WSL. Build in WSL/Linux, not on Windows: the sources and scripts need LF line endings (.gitattributes takes care of
    that in this repository).
  - Layers in conf/bblayers.conf: meta-hbbtv2 and meta-webkit in addition to the usual ones (config/dm900/bblayers.conf shows
    the working list, with the paths of the machine it was made on; the original is bblayers.conf.pre-wpe).
  - About 16 GB RAM. WebKit compile jobs are memory hungry: PARALLEL_MAKE is "-j 6 -k 0" in the bbappend (-j 8 ran out of memory
    on 16 GB). Plan on roughly 2 hours for a clean WebKit build at -j6.
  - Network for the first build: wpewebkit-2.54.0.tar.xz (wpewebkit.org) and the ORB git repository (github.com).

2. Set up
---------
  1. Copy (or symlink) meta-hbbtv2 next to the other layers and add it, and meta-webkit, to BBLAYERS.
  2. Nothing else: the recipes need no changes to local.conf for a normal build.

3. Build
--------
  cd builds/openvix/developer/dm900 && . ./env.source
  bitbake wpewebkit orb enigma2-plugin-extensions-wpehbbtv

  (tools/build/bb.sh does the environment part: "bb.sh <bitbake arguments>".)
  Order: wpewebkit (long) -> orb -> the plugin. Use -k if you want the others built when one fails.
  Long builds: if the shell you start it from ends the command after a while (e.g. a 10 minute limit), only the bitbake client
  dies - the bitbake server keeps building on its own. Start it detached instead:
      setsid nohup bash -c 'bash bb.sh -k wpewebkit orb enigma2-plugin-extensions-wpehbbtv >log 2>&1' </dev/null &
  Do not add "enigma2" (or anything that leads to it) to RDEPENDS of the plugin: bitbake then builds all of enigma2.

6. Development builds of WebKit (incremental)
---------------------------------------------
  A clean WebKit build takes about 2 hours, and OE deletes the build directory whenever do_configure runs again
  (cmake.bbclass: do_configure[cleandirs] = ${B}; externalsrc only spares directories inside the source tree). So for work on
  the WebKit patches build from a persistent, patched tree, exactly like the other packages in local.conf:

    a) make the tree (tarball + the 2 patches of meta-webkit + our 13, in this order):
         tar -xf sources/wpewebkit-2.54.0.tar.xz -C /home/alpha/wpe-src
         cd /home/alpha/wpe-src/wpewebkit-2.54.0
         for p in <meta-webkit>/recipes-browser/wpewebkit/files/000[12]-*.patch \
                  <meta-hbbtv2>/recipes-browser/wpewebkit/files/00*.patch; do patch -p1 -s < $p; done
       tools/build/verify_patch_series.sh does this in a temporary directory and compares the result with the dev tree
       (it printed only a dangling Cargo.toml symlink that exists on both sides = identical). tools/build/prep_src.sh is the
       older script that made the current tree (git baseline "patches 0001-0003", then one commit per patch).
    b) add the two lines of config/dm900/local.conf.hbbtv2 to local.conf (EXTERNALSRC:pn-wpewebkit, EXTERNALSRC_BUILD:pn-wpewebkit).
    c) edit the tree, then "bitbake wpewebkit": only the changed files are recompiled. When a change is done, turn it into a
       patch file in meta-hbbtv2/recipes-browser/wpewebkit/files/, in the same numbering (tools/history/patchNN.sh show how).

  The rule: do NOT change anything that reaches wpewebkit's do_configure while such a build is in progress - SRC_URI (that is why
  the bbappend adds patches 0003-0013 only when EXTERNALSRC is not set), local.conf variables for the recipe, its dependencies.
  After any such edit check before building:
         bitbake-diffsigs -t wpewebkit do_configure          (names the variable that changed; nothing = safe)
         cd /home/alpha/wpe-src/build && ninja -n -d explain all | head      (must not say "command line changed"/"deps ... missing"
                                                                              for everything)

7. ORB
------
  The ORB tree is not part of this repository: orb_git.bb fetches it (pinned SRCREV) and applies orb/files/0001-0003. To change
  the polyfill, edit the JavaScript in a checkout of https://github.com/OpenRedButtonProject/orb, rebuild with
      make build ORB_NATIVE=rdk BBC_API_ENABLE=0      (output: out/resources/assets/polyfill/*.js)
  and turn the change into orb/files/000N-*.patch (tools/build/orb_patch3.sh is an example). For a quick test copy the rebuilt
  hbbtv.js over /usr/lib/orb/hbbtv.js on the box (no restart needed, wpe_fb reads it at start).
  Diagnostics: /usr/lib/orb/debug.js forwards the application's console output, script errors, media events and rejected
  promises to /tmp/wpe_fb.log as "[page] ..." lines (delete the file to switch it off).

10. Applications of a channel (ARD, ...) - 2026-09-20
-----------------------------------------------------
  The plugin's "WPE HbbTV: channel app" reads the service enigma2 is tuned to (original network id, transport stream id, service id, name)
  and gives it to run_wpe.sh (WPE_CHANNEL), which sends "channel <onid> <tsid> <sid> <name>" to wpe_fb before "app <url>". The application
  is then started as a BROADCAST-RELATED application of that service (ORB patch 0004, orb_host_launch_broadcast): ORB answers its Broadcast.*
  requests (before: SecurityError, so the ARD start application drew nothing). The platform layer (orb_platform_wpe.cpp) answers
  getCurrentChannel / getChannelList with the tuned channel, reports it as "presenting" (ChannelStatusChanged) when the application takes
  over the broadcast presentation or selects the current channel, and returns a video and an audio component for it. Verified with ARD
  (headless probe, tools/box/app_probe.sh, and a run of the installed plugin): the start banner appears for ~9 s, RED opens the real
  start bar with live programme data. Not done yet: the components have no PIDs/languages (not read from the stream), the channel list
  is only the current channel, other channels cannot be tuned by an application (setChannel to another service is refused), no real
  AIT (autostart control codes, key sets and several applications per channel come from it), programme data from enigma2's EPG.
  Test one application: sh app_probe.sh <label> <url> <seconds> [keys...]  (PROBE_REF=1:0:19:283D:3FB:1:C00000:0:0:0: PROBE_NAME="Das Erste HD"
  to use another service than the tuned one; DUMP_AT="2 4 6 9" for screenshots at those seconds).

  Scrollbars and the ZDF banner (plugin r3, 2026-09-20):
  - ZDF's main application overflows the 1280x720 view for one to two seconds while it starts (document 1288x886..1368) until it sets
    overflow:hidden, so WebKit drew scrollbars. wpe_fb now installs a user style sheet that hides them (--scrollbars keeps them);
    measured with wpe_fb.p3 (edge pixels lit at t=3-4 s) against the fixed build (none).
  - (REVERTED in plugin r5 on the user's request - every channel starts with its own start application, ZDF too.) The AIT autostart URL of the ZDF channels (http://hbbtv.zdf.de/zdfstart/...) is only a banner; plugin r3/r4 started the media library
    (http://new-hbbtv.zdf.de, with ?mode=tivi|heute|3sat as the banner's LinkManager would add it) at once (plugin.py, mainAppUrl).

11. Fast frame read-back (WebKit patch 0013, plugin/webkit r1) - 2026-09-21
----------------------------------------------------------------------------
  glReadPixels on the DM900's vendor GLES runs at ~14 MB/s, so every large repaint cost 0.4-0.8 s at 1920x1080. Patch 0013
  (AcceleratedSurface.cpp, IonPixmapReadback) blits the bounding box of a frame's damage rectangles with the GPU into a pixmap surface on
  ION (BMEM) memory (eglCreatePlatformPixmapSurfaceEXT + struct dmegl_pixmap_handle) and copies the rectangles out with an NEON loop that
  swaps red and blue. Measured on ZDF at 1920x1080 (docs/spike-s1-results.txt has the background): full frame 850 -> 90 ms, typical partial
  frame 190-240 -> 50 ms, twice as many frames in the same time. WEBKIT_SHM_READBACK_PIXMAP: unset/1 = on, 0 = off (Skia readPixels as
  before), verify = on and every rectangle compared with Skia's read (logs "N px differ from Skia"; 0 in all tests). Any failure switches
  it off for the process. WEBKIT_SHM_READBACK_LOG=1 prints the per-frame times.
  Dev-build pitfalls found on the way:
   - "ninja -n -d explain" with the system ninja (1.11) reports "command line changed" for EVERY target: the log hashes of ninja 1.13 (the
     recipe's native ninja) differ. Use recipe-sysroot-native/usr/bin/ninja (of the wpewebkit work dir) for the check and for private builds.
   - The version bump for opkg is PKGR = "r1" in the bbappend (not PR: a PR test with "bb.sh -n" showed do_configure would run, and a re-run
     deletes /home/alpha/wpe-src/build). BUT the dry run is NOT a reliable safety check: on 2026-09-21 "bb.sh -n wpewebkit" listed no
     do_configure for the PKGR state, yet the real "bitbake wpewebkit orb ..." run re-ran do_configure, wiped the build directory and started a
     full rebuild (~1.5 h). What the signature files showed (python: bb.siggen.compare_sigfiles(old, new) on the two newest
     tmp/stamps/.../wpewebkit/2.54.0.do_configure.sigdata.* / do_unpack.sigdata.*; do not use bitbake-diffsigs while a build runs: it hangs on
     the busy server): the last configured state (2026-09-20 14:50) had patches 0003-0012 in SRC_URI, the current parse (bbappend guard
     "if EXTERNALSRC: return") has none, so do_unpack -> do_configure hashes differed. I could not establish when that difference arose.
     Rule: before a real bitbake run compare the newest sigdata files as above; if do_configure would differ, expect the full rebuild.
   - Private test of a new library: strip it (arm-oe-linux-gnueabi-strip --strip-unneeded), put it into /media/hdd/wpe-test/lib as
     libWPEWebKit-2.0.so.1 (keep the old one as .pre-...), run tools/box/app_probe.sh with PROBE_VIEW="--hidpi 1.5 --persist <dir>".
  Installed on the DM900 on 2026-09-21 (box idle, no GUI restart needed: wpe_fb is a separate process that loads the library when it starts):
      opkg install --no-install-recommends ./libwpewebkit-2.0-1_2.54.0-r1_*.ipk ./libwpewebkit-2.0-web-inspector-plugin_2.54.0-r1_*.ipk
  WITHOUT --no-install-recommends opkg would also install the package's Recommends (gstreamer1.0-plugins-{base,good,bad}-meta, fonts,
  ca-certificates): 199 packages from the box's feed. Verified headless with the installed stack (/usr/bin/wpe_fb, /usr/lib, script
  /media/hdd/wpe-test/pkg_check.sh): pixmap mode verify = 70 frames, 0 px differ; on: partial 50 ms / full 106 ms; off: 182 / 842 ms.

12. The streams of the channel: audio, video, subtitles (orb r2, plugin r4) - 2026-09-21
----------------------------------------------------------------------------------------
  What an application sees through video/broadcast.getComponents() used to be made up (one video, one audio, no PIDs). Now enigma2's real
  streams are handed over:
    plugin.py readComponents(service)      reads them (info.getInfo sVideoPID/sVideoType/sIsCrypted/sAspect, service.audioTracks(): PID,
                                           language, format, channels, current track; service.subtitle().getSubtitleList(); the selected
                                           subtitle from InfoBar.instance) and makes ONE line of the form
                                           V:<pid>:<enc>:<crypted>:<aspect>;A:<pid>:<lang>:<enc>:<channels>:<active>:<ad>;S:<pid>:<lang>:<enc>:<active>:<hi>
    before the start:                      env WPE_COMPONENTS -> run_wpe.sh (validated: only A-Za-z0-9:;.+-) -> ctl "components ..." before "app"
    afterwards:                            the plugin polls once a second and sends the line again when it changed (a new programme, a
                                           selection); ctl "components ..." -> orb_host_set_components() -> orb_platform_wpe.cpp
                                           Broadcast_GetComponents (ids video_<pid>/audio_<pid>/subtitle_<pid>, componentTag -1: enigma2 does
                                           not expose the PMT stream identifier) and OnComponentChanged / OnSelectedComponentChanged
    the application selects (selectComponent / unselectComponent -> Broadcast.overrideComponentSelection / restoreComponentSelection):
                                           platform -> orb_host_platform_select_component -> wpe_fb writes "select audio|subtitle <pid>|default|
                                           none" to the event FIFO (/tmp/wpe_fb.evt, exists with --hwvideo-lazy) -> the plugin's pollEvents ->
                                           audio.selectTrack(n) / InfoBar.instance.enableSubtitle(tuple); "default" audio = the track that was in
                                           use when the application started, subtitles default/none = off. The plugin then sends the new list
                                           (the "active" flags), which is what makes the application see the change.
  Limits: no audio description flag (enigma2 does not say), audio cannot be switched off, video cannot be switched; while the live service is
  stopped for the decoder handover the last list stays. Without any list the old made-up video + audio are still answered (an embedder run by hand).
  Tests: tools/box/test_components.py (stub enigma2 objects, runs anywhere with python3), tools/box/comp_check.sh + pages/orb_components.html
  (headless on the box with the installed stack; the script plays the plugin) - result 2026-09-21: the page sees the 5 components with real PIDs,
  selectComponent(audio 5103) arrives as "select audio 5103", the new list gives SelectedComponentChanged / ComponentChanged and the active
  audio is 5103 afterwards. Not tested yet: the plugin against the real enigma2 (needs a GUI restart after installing plugin r4).
  Note for test pages: getComponents(-1) filters for type -1 in the polyfill; no argument (or the type) is what returns components.

13. The real AIT (orb r3, plugin r8) - 2026-09-21
--------------------------------------------------
  Before: the plugin started the one URL enigma2 keeps for the AUTOSTART application (sHBBTVUrl) as a made-up broadcast-related application (ORB patch
  0004); the engine had no AIT, so dvb://current.ait/... links of an application ("No AIT, early out") did not work and nothing else the channel
  signals was known. Now the plugin reads the AIT itself and the ENGINE runs the lifecycle:
    reading:   AitReader (a thread in plugin.py) opens a section filter on /dev/dvb/adapter0/demux<N> (N = sLiveStreamDemuxId of the playing service,
               a second filter next to enigma2's), waits for the PMT of the service (sid + sPMTPID), takes the PID of the ES with an
               application_signalling_descriptor (0x6F), and follows the AIT on it (table 0x74), reporting every new or changed section.
               The demux needs DMX_SET_BUFFER_SIZE (0x6F2D) before the filter, and struct dmx_sct_filter_params has its 2 padding bytes BEFORE
               timeout (60 bytes: pid, filter[16], mask[16], mode[16], pad, timeout, flags) - both cost me an afternoon; tools/box/ait_probe.py
               prints what a service signals, ait_capture.py writes the sections to a file (tools/box/testdata/ait_zdfhd.txt = ZDF HD, 10 applications).
    choosing:  "WPE HbbTV: channel app" shows "Reading the HbbTV application information ..." while the AIT is read (a second or two); with one usable
               application (AUTOSTART or PRESENT, transport HTTP) it starts, with several a list is offered (autostart first). No readable AIT: the old
               sHBBTVUrl route.
    starting:  page argument "ait:" (the AUTOSTART application) or "ait:<org hex>.<app hex>"; run_wpe.sh sends "channel", "components", "service <onid> <tsid>
               <sid>", every AIT section as "ait <pid> <sid> <hex>" (file /tmp/wpe_ait.txt, WPE_AIT), and for another application
               "app dvb://current.ait/<org>.<app>". wpe_fb -> orb_host_service_selected / orb_host_ait_section / orb_host_broadcast_stopped -> the engine's
               OnChannelStatusChanged(CONNECTING) / OnAitSectionReceived / OnBroadcastStopped: ORB starts the autostart application (isBroadcast=1),
               resolves locators, kills what the AIT no longer signals. THE LOCATOR IS HEXADECIMAL (org 17 / app 3 = dvb://current.ait/11.3).

14. Red button and automatic banner (orb r4, plugin r14) - 2026-09-21
----------------------------------------------------------------------
  Two ways to start the application of a channel, each with its own switch in the plugin's settings:
    red button (WPE_REDBUTTON, default on):  enigma2's InfoBar.onHBBTVActivation hook (InfoBarRedButton.activateRedButton) starts the channel application
               as a screen of its own and presses red for it once it has loaded (RED_DELAY 1500 ms after the event "loaded").
    automatic banner (WPE_AUTOSTART, default off):  class AutoStart (plugin.py). When the box has stayed on a service for 3 s (SETTLE) it reads the AIT
               (section 13); with an AUTOSTART application the banner runs on top of the live picture, keyed by the engine's key set:
               wpe_fb reports "keyset <mask>" (orb_host_key_set_mask, every 300 ms) and an eActionMap hook (bindAction "", highest priority) takes ONLY the keys
               of that mask (red/green/yellow/blue, navigation, VCR, numeric; EXIT only once the navigation keys are asked for) and passes their "make",
               repeat and "break" to the application; everything else stays enigma2's. Zapping to another service stops the banner; a service that stops
               only because the application takes the decoder for media does not.
  HOW THE BANNER IS SHOWN (the decision that cost the most): wpe_fb --overlay-png /tmp/wpe_overlay (run_wpe.sh, WPE_OVERLAY=1). The frame is NOT written into
  the framebuffer. For every change (at most 10/s, PNG_INTERVAL_MS) wpe_fb saves the bounding box of the visible pixels as an UNCOMPRESSED PNG
  (wpe_fb_png.h: deflate "stored" blocks, own CRC/Adler, no zlib; straight alpha) and writes "overlay <n> <x> <y> <w> <h> <file>" (or "... 0 0 0 0 -")
  to the event FIFO. The plugin's WPEScreen(overlay=True) is a dialog (instantiateDialog + show()) with a skin of 1x1 and one Pixmap widget; it moves and
  resizes ITSELF to the bounding box and does widget.setPixmapFromFile(file): enigma2 composes it with the rest of its screen (a user's suggestion:
  "a skin screen with a pixmap"). Only the newest event of a poll batch (100 ms) is decoded; wpe_fb keeps the last 4 files.
  WHY NOT THE FRAMEBUFFER (three hardware runs to learn it): gEGLDC::flip() presents page N, then seeds the next render page with a copy of N at that very
  moment - before anything of ours is painted into N - so every page enigma2 presents after a flip lacks the overlay until a repaint (blinking once
  a second while the infobar or a message updates; the repaint of 150 k pixels took 74 ms); and an "under" pixel captured for one page is wrong for the next
  (a hidden box restored a stale black rectangle when its hide raced a flip). Writing behind enigma2's back cannot be made robust. The full-screen (red
  button) mode still uses the framebuffer with the guard, which is fine there because enigma2 has nothing else to show.
  Bugs on the way (all invisible to the first tests, all now covered by tools/box/test_autostart.py, which uses the REAL WPEScreen with stubs and is
  checked to fail without each fix):
    - start() ran twice for a dialog (once by AutoStart, once by onLayoutFinish); the second execute() returned -1: "could not start wpe_fb" and the good

  Measuring flicker: tools/box/infobar_monitor.py (+ zap_run.sh) logs, for every page flip of /dev/fb0, how many sample points of the infobar band are
